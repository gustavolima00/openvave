# Research: Read-only BLE connection to the Tank-G

Phase 0 output for [plan.md](plan.md). Each entry: Decision / Rationale / Alternatives.

## R1. Language and runtime

- **Decision**: Python ≥ 3.11, packaged with a `pyproject.toml` (hatchling backend), managed
  with `uv`.
- **Rationale**: the exploration POC (`poc/probe_readonly.py`, not committed) already ran the full
  read-only connect sequence on real hardware in Python 3.11 + `bleak`, so the BLE behaviour this
  spec depends on is proven on this stack. Python is also the most common language among
  hobbyist pedal/MIDI tooling, which helps Constitution I (others reuse the library).
  3.11 gives `asyncio.timeout()` and `ExceptionGroup`, both used below.
- **Alternatives**: Rust (`btleplug`) — single static binary, but the BLE behaviour would have to
  be re-proven and contributors are fewer; TypeScript/Node (`noble`) — weak Windows/macOS
  maintenance; Go (`tinygo-org/bluetooth`) — limited macOS notify support.

## R2. BLE stack

- **Decision**: `bleak` (≥ 0.22) as the only runtime dependency, wrapped in one `BleakTransport`
  class behind the transport interface (Constitution VII).
- **Rationale**: one API over CoreBluetooth (macOS), BlueZ/D-Bus (Linux) and WinRT (Windows);
  used by the POC; actively maintained; asyncio-native, matching the request/response model.
- **Alternatives**: `simplepyble` (sync, C++ build, smaller community); platform-native
  bindings per OS (three implementations for no gain).

## R3. Concurrency model of the library API

- **Decision**: async-first library (`async with TankG.connect(...)`), no sync wrapper in this
  feature. The CLI calls `asyncio.run()` once per command.
- **Rationale**: `bleak` is asyncio-only; a sync facade would need a background loop thread and
  is YAGNI until a concrete caller needs it.
- **Alternatives**: sync facade now (adds a thread + loop lifecycle; rejected per VII).

## R4. CLI framework

- **Decision**: standard-library `argparse`; entry point `openvave` (and `python -m openvave`).
- **Rationale**: two subcommands (`info`, `preset dump`) and a handful of flags do not justify a
  dependency (VII). `argparse` already exits with status 2 on usage errors.
- **Alternatives**: `click` / `typer` (nicer help, but extra runtime deps for little gain).

## R5. Test stack

- **Decision**: `pytest` + `pytest-asyncio` (dev only), `jsonschema` (dev only, validates CLI
  JSON against `contracts/*.schema.json`), `ruff` (lint+format), `mypy --strict` on `src/`.
  Hardware tests are marked `@pytest.mark.hardware` and skipped unless `--hardware` is passed;
  CI never passes it.
- **Rationale**: Constitution III requires a hardware-free default suite and opt-in hardware
  tests; marker + CLI option is the idiomatic pytest mechanism. Dev-only deps do not affect users.
- **Alternatives**: `unittest` (more boilerplate for async and parametrised fixture tests);
  hand-written JSON checks instead of `jsonschema` (the schema is a published contract, so it
  should be machine-checked).

## R6. Fixture provenance (spec FR-022, clarification Q2)

- **Decision**: commit a sanitized copy of `captures/private/20261116-111832-probe.jsonl` as
  `captures/fw96/20261116-probe-connect.jsonl`, plus a `captures/README.md` describing the
  JSONL format (`t`, `event` ∈ {`tx`, `rx-chunk`, `rx`}, `label`, `hex`) and a provenance header
  (firmware 96, macOS, ATT MTU 185, date, tool). Tests load fixtures only from `captures/`
  through one loader; negative cases are generated by named mutation helpers applied to those
  frames (flip checksum, change echoed command, change echoed address/length, truncate, split
  into N chunks).
- **Rationale**: satisfies Constitution II (every fixture cites a capture) and III (tests use
  real bytes); mutations are explicit and reviewable.
- **Observation**: in this capture every reply arrived in **one** notification (MTU 185 ≥ 47 B,
  the largest reply). Multi-notification reassembly is therefore *not* exercised on hardware yet;
  it is tested only by splitting real frames (mutation `split(n)`), and the protocol docs keep
  reassembly at `observed` (from the app's code), not `confirmed`.

## R7. Sanitization of the device-info block

- **Decision**: before committing the capture, check whether the 3 unknown bytes at offsets
  19–21 of the device-info block (`b7 43 f3`) match any part of the pedal's BLE or Classic
  Bluetooth MAC address or serial number. If they do, the committed capture replaces them with a
  documented placeholder (`00 00 00`) **and recomputes the checksum**, the capture file records
  `"sanitized": ["devinfo[19:22]"]`, and tests treat those bytes as opaque. If they do not match,
  they are committed unchanged and documented as unknown.
- **Rationale**: Constitution VI requires sanitizing device identifiers; three non-zero bytes in
  an "info" block are a classic place for a MAC/serial fragment. Recording the substitution keeps
  the fixture honest about what was changed.
- **Alternatives**: always redact (loses possibly useful data if they are e.g. a build id);
  never check (risks leaking an identifier).

## R8. Device discovery and selection

- **Decision**: scan for up to `--scan-timeout` seconds (default 5 s) and match the advertised
  local name exactly `TANK-Gv2_BLE` (confirmed). `--device ID` skips the name filter and connects
  to that platform identifier (MAC on Linux/Windows, CoreBluetooth UUID on macOS). If more than
  one pedal matches and no `--device` is given, exit with a dedicated code and list candidates
  (identifier, name, RSSI) on stderr. The Classic identity `TANK-Gv2` (no `_BLE`) never matches.
- **Rationale**: exact match on the confirmed name avoids false positives; explicit selection
  matches the spec edge case "never silently pick one". A `openvave scan` command is not needed:
  the ambiguity error already lists candidates (YAGNI).
- **Alternatives**: match the BLE-MIDI service UUID (shared by many MIDI devices); match prefix
  `TANK-G` (untested for other models).

## R9. Timeouts and retries

- **Decision**: per-request timeout 2.0 s (`--timeout`); handshake retried up to 3 attempts
  (FR-007) with the same timeout each; read requests are not retried (a failed read is a
  protocol/connection error); after enabling notifications, wait 200 ms before the first command,
  as the app does. Worst case success path ≈ 5 s scan + connect + 5 × ~0.1 s, inside SC-001's
  10 s.
- **Rationale**: observed replies arrive in 40–90 ms; 2 s is generous yet bounded
  (constitution: time out instead of hanging).
- **Alternatives**: retry reads too (masks real errors; reads are deterministic, so a failure is
  meaningful).

## R10. Safety enforcement (FR-010, FR-011, SC-004)

- **Decision**: the frame encoder accepts only command bytes in a module-level allowlist
  `{0x11, 0x23}` and raises `UnsafeCommandError` otherwise; read requests can only be built from
  the closed `Region` enum (the four FR-008 regions) — there is no public "read address" API. A
  session-wide pytest fixture wraps every `FakeTransport` and fails the test run if any sent
  frame's command byte is outside the allowlist (SC-004 audit).
- **Rationale**: makes writes impossible by construction in this feature rather than by
  convention; future write support will be a separate, explicitly named API (Constitution IV).
- **Alternatives**: document "don't call write" (not enforceable).

## R11. Hex trace (FR-018)

- **Decision**: standard `logging` logger `openvave.trace` at DEBUG, one line per frame:
  `TX|RX <hex>` (RX per notification chunk and per reassembled frame). Silent by default; the CLI
  `--trace` flag attaches a stderr handler.
- **Rationale**: no dependency, library users can route it anywhere; matches the constitution's
  logging constraint.

## R12. JSON output contract (clarification Q4)

- **Decision**: JSON Schema (draft 2020-12) files in `contracts/` for `info` and `preset dump`;
  `schema_version` starts at `1`. Raw region data is always emitted as lowercase space-separated
  hex (same format as `captures/`). Decoded fields appear under `fields` with a `confidence`
  attribute. `read_at` (ISO 8601 UTC) is the only time-varying field (SC-006).
- **Rationale**: machine-checkable contract, diffable output, additive evolution.

## R13. Exit codes (FR-016)

- **Decision**: `0` ok · `1` unexpected internal error · `2` usage error (argparse) ·
  `3` no pedal found · `4` multiple pedals, none selected · `5` Bluetooth unavailable / permission
  denied · `6` connection lost or timeout · `7` protocol error (bad checksum, wrong echo,
  handshake failed after retries).
- **Rationale**: distinct codes for the categories the spec requires plus the two discovery edge
  cases; stable codes are part of the CLI contract.

## R14. Firmware gating (clarification Q1)

- **Decision**: `TESTED_FIRMWARE = frozenset({96})`. If the handshake version is not in it, the
  session sets `identity.firmware_untested = True`, logs a warning (`openvave` logger), the CLI
  prints `warning: firmware 97 is untested (tested: 96); byte layouts may differ` on stderr, and
  all reads proceed.
